otter's window climber (`climber.go`) is a line-by-line port of Caffeine's `WindowClimber`, and
its sketch and policy follow Caffeine's (see `design-decisions.md`). This skill checks the
port: it runs Caffeine's simulator (`product.Caffeine`) and otter's simulator on the same key
streams and reports, per cell (trace, capacity), whether the hit rates are equal.

Run it after any change to `climber.go`, `policy.go` or `sketch.go`, and when the port follows a
newer Caffeine commit. `/sim-compare` answers a different question (did otter's hit rate move
between two revisions); this one answers "does otter still decide as the reference does".

## Input

$ARGUMENTS

Default: the whole pipeline against Caffeine `master`, with the uncommitted worktree as otter.

## Why the hit rates can be equal

otter hashes sketch keys with a random per-cache seed, so on small traces two runs of otter
differ by points. `build` compiles otter's simulator with one change: the sketch hashes a key as
Caffeine does (`Long.hashCode`, then its 32-bit `spread` and `rehash`). With equal hashing the
two caches take the same decisions, and the only nondeterminism left on either side is the
random admission of a warm candidate (1 in 128 of the comparisons where the candidate is not
more frequent but at least 6). Cells where that never fires come out equal to a hundredth;
elsewhere the difference stays within the spread of repeated runs.

## Pipeline

All state goes under `.local/parity/` (gitignored). Run from the repository root.

```bash
P=.claude/skills/sim-parity/parity.py
JAVA_HOME=<JDK 25+> python3 $P setup [--ref master]   # clone Caffeine, build its simulator
python3 $P traces [--large]       # rewrite real traces to LIRS, generate the traps
python3 $P build [--ref WORKTREE] # otter's simulator with Caffeine's sketch hash
python3 $P run [--only REGEX] [--reps 3] [--otter-reps 3] [--jobs N]
python3 $P report [RUN_DIR]       # reprint a run's table
```

- **setup**: the first build downloads Gradle and about 1 GB of dependencies and takes ~10
  minutes. Gradle provisions the JDK its daemon wants (`gradle-daemon-jvm.properties`, 26 at the
  time of writing) into `GRADLE_USER_HOME/jdks`, and the simulator's classes target it, so the
  script runs the simulator with that JDK (override with `PARITY_JAVA`). On a slow network,
  download `gradle-*-bin.zip` with curl into the wrapper's `dists` directory first.
- **traces** writes `.local/parity/traces/manifest.tsv` (name, path, capacities):
  - the unweighted traces bundled with Caffeine's simulator (lirs, address, cache2k,
    cloud_physics w106, corda, scarab), rewritten by its `Rewriter` to LIRS so that both
    simulators read one key stream; capacities at 5–75% of the distinct keys;
  - otter's ARC traces (`benchmarks/simulator/trace/arc`) at the capacities of the
    `sim-compare` configs;
  - the climber's adversarial traps, generated by the scripts in `traps/` (copied from
    Caffeine's `climber-gate` and `audit-regret` skills, deterministic and seeded) at the cache
    sizes Caffeine's gate runs them at, including the tier straddle at 4096 and 4097;
  - `--large` adds S3, DS1, corda-large, scarab-recs-large and the two 10M+ request traps.
- **build** copies the tree (`WORKTREE` or a git ref) to `.local/parity/otter-<ref>`, replaces
  the sketch's `hash` and `rehash`, and builds the simulator. If `sketch.go` changed shape, the
  script stops: update `HASH_FROM`/`REHASH_FROM` in `parity.py`.
- **run** interleaves the reference's repetitions (one JVM per cell) with otter's (one process
  per trace) and writes `results.csv` and `summary.txt` to `.local/parity/runs/<timestamp>/`.
  The default set takes about 30–60 minutes on 8 parallel jobs; `--only` narrows it.

## Reading the result

Each cell gets a verdict:

- `exact`: equal to the printed two decimals;
- `noise`: within three standard deviations of the repeated runs (at least 0.05);
- `CHECK`: too few repetitions to tell; rerun the trace with `--only` and more `--reps` and
  `--otter-reps`;
- `MISMATCH`: outside the noise with at least three repetitions on each side.

Several traps are bimodal: one admission draw sends the cache into one of two basins, and both
sides spread by points (rep_r6_w4096 ±23, slowswap_r1 and phases ±7–8, the moats ±3). Judge them
by the mean of eight runs and by whether the two sides land in the same basins, never by a draw.
On the first full run (2026-10-15, 272 cells) all three MISMATCH cells at three repetitions
became noise at eight.

A MISMATCH is a departure of the port, not a tuning question. To find it:

1. Rerun the cell with `--reps 8 --otter-reps 8` to rule out a lottery.
2. Look for a pattern: one tier only (`> 4096` is the density tier, `<= 512` the slow reactive
   one), one family of traps, or every cell of a trace.
3. Diff the code paths against the reference at the commit in the run's `meta.json`
   (`.local/parity/caffeine`): `WindowClimber.java` for the climber, `BoundedLocalCache.java`
   (`climb`, `onAccess`, `AddTask`, `UpdateTask`, `evictFromMain`, `admit`) and
   `FrequencySketch.java` for the rest. Typical Go pitfalls: an untyped constant expression
   evaluated exactly where Java rounds each step (declare such constants as `float64`), a
   `float64 → int64` conversion out of range, unsigned arithmetic where Java's is signed, and
   negative zero.
4. When the departure is intended (an otter design decision), record it in
   `design-decisions.md` and expect the cells it touches to differ.

The traps' meaning (what each attacks, and what Caffeine's numbers on them are) is documented
in Caffeine's `.claude/skills/climber-gate/SKILL.md` and `.claude/docs/hill-climber.md`; read
them there when a trap is the one that moves.

## Report

Return the run's summary line, the MISMATCH and CHECK cells (if any) with the reference and
otter numbers, and for each MISMATCH the code path found in step 3. Say which trace sets were
not run (`--large`, `--only`) and why.
